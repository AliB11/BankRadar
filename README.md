# بانک‌رادار · رادار محصولات بانکی ایران

سامانه مقایسه، رتبه‌بندی و پایش محصولات بانکی ایران — سپرده‌ها، اعتبار، تسهیلات و باشگاه‌های امتیازی — با
امتیازدهی شفاف از دید مشتری و **تعدیل‌شده نسبت به تورم**.

> نرخ اسمی به‌تنهایی کافی نیست: تورم، هزینه‌های جانبی، شرایط قرارداد و کیفیت منبع نیز مهم‌اند.
> اعداد این سامانه تخمینی‌اند و جایگزین تأیید بانک یا قرارداد نیستند. [گزارش ممیزی ۱۱ آبان ۱۴۰۵](docs/AUDIT_2026_11_02.md) حدود پوشش و منابع را توضیح می‌دهد.

## قابلیت‌ها

**مقایسه و تحلیل**
- ۳۶۱ رکورد از جمله موارد تاریخی، در پنج دسته: سپرده (۵۳)، صندوق (۷۳)، اعتبار (۶۵)، تسهیلات (۱۵۶) و امتیازی (۱۴)؛ فهرست نهادها شامل ۷۸ بانک، مؤسسه، فین‌تک و مدیر صندوق است
  (شمار دقیق و زنده در خود سامانه نمایش داده می‌شود و با هر واکشی عوض می‌شود)
- **بخش مجزا برای صندوق‌های سرمایه‌گذاری با درآمد ثابت (Fixed-Income Funds)**: ۷۳ صندوق فعال (۴۳ ETF + ۳۰ صدور/ابطالی) با سنجهٔ یکسانِ «بازدهی محقق‌شدهٔ یک‌ساله» از آی‌سیگنال (تا ۴۳٪)، قیمت صدور/ابطال، ضامن نقدشوندگی، نوع تقسیم سود (ماهانه/انباشته) و رتبه‌بندی جذابیت اختصاصی
- **پایش سودهای ترجیحی گزارش‌شده**: نردبان نرخ‌های توافقی (۲۲ تا ۳۱ درصد) به تفکیک مانده برای سپرده‌های کلان، به‌همراه طرح‌های ویژه خارج از سقف متعارف
- امتیاز «جذابیت» ۰ تا ۱۰۰ با پنج بعد وزن‌دهی‌شدنی و پنج پروفایل آماده
- **بازده حقیقی** بر پایه رابطه فیشر: نرخ اسمی در برابر تورم، با نمایش صریح فرسایش قدرت خرید
- **ماشین‌حساب اقساط** با هر دو روش رایج بانکی (اقساط مساوی و سود مازاد) و محاسبه نرخ مؤثر
- جدول مقایسه کنار‌به‌کنار با برجسته‌سازی مقادیر برتر هر معیار
- **فیلتر نوع عقد** در تسهیلات و اعتبار: تفکیک قرض‌الحسنه، عقود غیرمشارکتی (مبادله‌ای) و مشارکتی
- نمودار نردبان نرخ‌ها در برابر خط تورم و نقشه حرارتی تازگی داده

**کیفیت داده**
- هر رکورد دارای منبع، نوع منبع، سطح اطمینان و تاریخ کنترل است
- رکوردهایی که در واکشی دیده نشوند **حذف نمی‌شوند**؛ با نشان «نیازمند بازبینی» علامت می‌خورند
- اعتبارسنجی طرح‌واره در CI؛ در صورت خطا، انتشار متوقف می‌شود
- خروجی JSON و CSV برای استفاده در تحلیل‌های دیگر

**تجربه کاربری**
- **تم روشن و تیره** با انتخاب کاربر و تشخیص خودکار از تنظیم سیستم؛ بدون «فلش تم نادرست» در بارگذاری اولیه
- **خروجی اکسل واقعی (.xlsx)** سه‌برگه‌ای — محصولات فیلترشده یا سبد مقایسه، شاخص‌های کلان و خلاصه — با برگه‌های راست‌به‌چپ، سربرگ منجمد و سلول‌های عددی قابل فرمول‌نویسی؛ تولید بومی و بدون هیچ وابستگی خارجی (`assets/js/xlsx.js`)
- کارت محصول با «نرخ درشت» به‌عنوان عنصر اصلی؛ نوار رتبه‌بندی نرمال‌شده روی گسترهٔ همان فهرست تا تفاوت امتیازهای نزدیک دیده شود
- تب‌های دسته در فهرست‌های بلند می‌چسبند؛ استایل چاپ گسترده‌تر برای گزارش کاغذی

**مهندسی**
- بدون وابستگی خارجی در زمان اجرا (نه فریم‌ورک، نه کتابخانه نمودار)
- بدون سرور؛ روی GitHub Pages یا حتی با باز کردن مستقیم فایل کار می‌کند
- آزمون‌های واحد برای تبدیل تقویم شمسی، تجزیه متن فارسی، ادغام داده، محاسبات مالی و امنیت قالب‌ها

## شروع سریع

نیازمندی: Node.js نسخه ۲۰ یا بالاتر. هیچ وابستگی خارجی نصب نمی‌شود.

```bash
git clone <repo-url> && cd <repo>

npm run serve          # پیش‌نمایش روی http://localhost:4173
npm test               # اعتبارسنجی داده + اجرای همه آزمون‌ها
npm run collect        # واکشی تازه از منابع و به‌روزرسانی داده
npm run collect:dry    # واکشی آزمایشی بدون نوشتن
npm run collect:offline # فقط بازسازی بسته؛ بدون شبکه و بدون تغییر تاریخ/گزارش گردآوری
```

باز کردن مستقیم `index.html` هم کار می‌کند: داده از `data/bundle.js` بارگذاری می‌شود تا
محدودیت CORS در محیط `file://` مشکلی ایجاد نکند.

### چرا بدون فریم‌ورک؟

این پروژه یک سامانه داده‌محور با تعامل محدود است. استفاده از فریم‌ورک، حجم بسته را چند برابر می‌کرد
بی‌آنکه قابلیتی اضافه شود. ماژول‌های ES بومی مرورگر، تقسیم مسئولیت تمیزی فراهم می‌کنند و
نتیجه در هر مرورگری بدون مرحله ساخت اجرا می‌شود.

### قاعده RTL در CSS (درس یک اشکال واقعی)

ویژگی‌های منطقی مثل `inset-inline-start` با جهت سند عوض می‌شوند، اما `translateX` **فیزیکی**
است و همیشه منفی یعنی چپ. کشوی جزئیات به لبه شروع چسبیده (در RTL یعنی لبه راست) و حالت
بسته‌اش با `translateX(-102%)` نوشته شده بود؛ نتیجه آنکه کشو به‌جای رفتن به بیرون، به وسط
صفحه می‌آمد و یک قاب تمام‌قد روی کل محتوا می‌نشست.

قاعده‌ای که حالا رعایت می‌شود و `tests/css.test.mjs` آن را قفل کرده است:

1. جهت جابه‌جایی عنصرِ بیرون‌صفحه باید با جهت سند هم‌خوان شود
   (`[dir='rtl'] .drawer { transform: translateX(102%) }`).
2. لایه‌های ثابتِ تمام‌صفحه در حالت بسته هم `visibility: hidden` و هم `pointer-events: none`
   می‌گیرند تا حتی در صورت خطای هندسی، چیزی روی صفحه نماند.
3. آزمون، هندسه جعبه را برای عرض‌های ۳۶۰ تا ۱۹۲۰ پیکسل بازسازی می‌کند و اگر لایه‌ای
   در حالت پیش‌فرض روی صفحه دیده شود، CI سرخ می‌شود.

## خط لوله گردآوری داده

`tools/collect.mjs` پنج منبع را موازی و مقاوم به خطا واکشی می‌کند:

| منبع | فایل | روش | خروجی |
| --- | --- | --- | --- |
| **رده (rade.ir)** | `tools/sources/rade.mjs` | کشف از `loan-sitemap.xml`، استخراج جدول مشخصات بر پایه **برچسب** نه سلکتور CSS | محصولات خودکار با `rade-<id>` |
| **سایت بانک‌ها** | `tools/sources/banks.mjs` | پایش ۲۵ هدف بانکی/نظارتی، استخراج نرخ و شرط با الگوی متنی | مشاهدات نرخ برای تأیید |
| **شاخص‌های کلان** | `tools/sources/cbi.mjs` | ثبت مشاهده جداگانه؛ انتشار خودکار تورم فقط با منبع معتبر و دوره جدید، نرخ سیاستی نیازمند تأیید | `indicators.json` |
| **دیجی‌شهر (مجله)** | `tools/sources/dgshahr.mjs` | جدول‌های نرخ سود سپرده بانک‌ها: نرخ‌های ترجیحی پلکانی + طرح‌های ویژه؛ طبقه‌بندی سلول بر پایه محتوا (ستون‌های جابه‌جایی‌یافته) و باز کردن rowspan | محصولات `deposits/preferential` و طرح‌های ویژه |
| **آی‌سیگنال (isignal.ir/fund)** | `tools/sources/isignal.mjs` | فهرست صندوق‌ها از همان API که صفحهٔ `/fund/` می‌خواند (POST `signalData/list`)؛ فقط نوع‌های «درآمد ثابت» (typeId 30/43)؛ جدول شناخت `KNOWN_FUNDS` برای شناسهٔ پایدار، نهاد مدیر و نوع تقسیم سود؛ برش برون‌خط با `ISIGNAL_JSON_FILE` | محصولات `funds` (`fund-<slug>`) با بازدهی یک‌ساله، قیمت صدور/ابطال، NAV و ضامن در `extra` |

### اصول طراحی خط لوله

۱. **حفظ داده و تفکیک مشاهده.** فیلدهای ساختاری رکورد دست‌نویس محافظت می‌شوند، اما برخی مقادیر آن ممکن است با مشاهده زنده به‌روز شوند. snapshot آفلاین محصول موجود را بازنویسی یا تازه نمی‌کند؛ رکورد خودکارِ دیده‌نشده حذف نمی‌شود و در صورت کهنگی `stale` می‌گیرد.

۲. **شکست یک منبع، اجرا را متوقف نمی‌کند.** هر منبع در `runSource` پیچیده شده و خطا در
   `meta.json` ثبت می‌شود؛ بقیه منابع به کار خود ادامه می‌دهند.

۳. **تطبیق دو‌مرحله‌ای.** تطبیق ابتدا با `id` و در صورت نبود، با کلید `bank::product` انجام می‌شود
   تا تغییر شناسه در منبع، رکورد تکراری نسازد.

۴. **خروجی پایدار.** کلیدهای JSON بازگشتی مرتب می‌شوند تا `git diff` فقط تغییرات معنادار را نشان دهد.

۵. **چرخش اکتشاف.** بخشی از ظرفیت روزانه رده به URLهای قدیمی‌ترِ کل sitemap اختصاص دارد، حتی اگر هرگز در مجموعه ثبت نشده باشند؛ چرخش وابسته به تاریخ است و برای sitemap ثابت پوشش تدریجی می‌دهد.

۶. **استخراج بر پایه برچسب.** صفحات رده جدول مشخصاتی با برچسب‌های ثابت دارند
   («نرخ سود وام»، «سقف وام»، «نوع ضمانت»). این روش در برابر تغییر قالب مقاوم است،
   برخلاف سلکتور CSS که با هر بازطراحی می‌شکند.

### اجرای خط لوله

```bash
node tools/collect.mjs                  # واکشی کامل
node tools/collect.mjs --limit=40       # محدودکردن تعداد صفحات
node tools/collect.mjs --dry-run        # بدون نوشتن
node tools/collect.mjs --offline        # بدون شبکه
node tools/collect.mjs --verbose        # گزارش کامل JSON
node tools/data-signature.mjs --json    # امضای محتوایی داده + شمارش‌ها
```

### امضای داده: تفکیک «تغییر واقعی» از «مهر زمانی»

`tools/data-signature.mjs` اثر انگشت محتوای داده را می‌سازد: محصولات، شاخص‌ها، بازه‌های
مصوب و فهرست بانک‌ها — **بدون** فیلدهای فرار (`generatedAt`، `lastRun`، مدت واکشی).

چرا لازم است: `products.json` در هر اجرا مهر زمانی تازه می‌گیرد، پس `git diff` همیشه
پر است. اگر ملاک کامیت همان diff باشد، هر اجرا — حتی وقتی هیچ منبعی پاسخ نداده —
یک کامیت بی‌محتوا و یک انتشار بیهوده می‌سازد. با امضا، تنها وقتی کامیت ساخته می‌شود
که واقعاً چیزی عوض شده باشد.

`lastSeen` و `lastVerified` عمداً بخشی از امضا هستند: تغییرشان یعنی خط لوله رکوردی را
بازبینی کرده، که یک به‌روزرسانی معنادار است.

## به‌روزرسانی خودکار با GitHub Actions

### `.github/workflows/refresh-data.yml`

| زمان‌بندی | توضیح |
| --- | --- |
| `30 3 * * *` | هر روز، ۰۷:۰۰ به وقت تهران — پیش از شروع روز کاری بانک‌ها |
| `0 5 * * 4` | هر پنجشنبه — بازبینی هفتگی جامع‌تر |
| دستی | از تب Actions با امکان تعیین محدودیت و حالت آزمایشی |

مراحل اجرا:

```
دریافت مخزن → Node 22 → امضای داده پیش از اجرا → واکشی داده → اعتبارسنجی
   → آزمون‌ها → بازسازی بسته → مقایسه امضا → ثبت و push (فقط اگر محتوا عوض شده باشد)
   → راه‌اندازی انتشار Pages (فقط در main و با تغییر واقعی)
   → گزارش تشخیصی → خلاصه اجرا → (در شکست) دم لاگ + ایشو اطلاع‌رسانی
```

نکته حالت اجرا: رویداد `schedule` ورودی (`inputs`) ندارد؛ حالت پنجشنبه از خود
عبارت cron تشخیص داده می‌شود (`github.event.schedule`) تا «بازبینی هفتگی جامع‌تر»
واقعاً در حالت هفتگی (`sync-weekly.mjs`) اجرا شود، نه واکشی روزانه ساده.

نکات پیاده‌سازی مهم:

- **پوسته bash با pipefail**: خروجی واکشی با `| tee collect.log` هم به لاگ می‌رود هم به
  کنسول. در پوسته پیش‌فرض Actions (بدون pipefail) کد خروج `tee` ملاک است، یعنی شکست سخت
  `collect.mjs` بی‌صدا رد می‌شد و اجرا «موفق» گزارش می‌کرد. با `defaults.run.shell: bash`
  این حفره بسته شده است.
- **ثبت شرطی بر پایه امضا**: اگر امضای محتوایی داده تغییر نکند، هیچ کامیتی ساخته نمی‌شود
  و انتشار بیهوده‌ای رخ نمی‌دهد (فقط مهرهای زمانی عوض شده‌اند).
- **همگام‌سازی پیش از push**: `git pull --rebase` پیش از `git push origin HEAD:<branch>`؛
  اگر بین واکشی و ثبت، کامیت دیگری روی شاخه نشسته باشد، به‌روزرسانی آن روز رد نمی‌شود.
- **دروازه کیفیت**: اگر `validate-data.mjs` یا آزمون‌ها شکست بخورند، تغییرات هرگز commit
  نمی‌شوند؛ سامانه با آخرین داده معتبر به کار ادامه می‌دهد.
- **اطلاع‌رسانی شکست**: در صورت خطا، ایشویی با برچسب `data-pipeline` ثبت (یا به ایشو باز
  موجود اضافه) می‌شود. برچسب‌ها پیش از استفاده **در خود جریان کاری ساخته می‌شوند**، چون
  ایشو با برچسب ناموجود خطای 422 می‌گیرد و همان اطلاع‌رسانی از دست می‌رود.
- **خلاصه اجرا**: سلامت هر منبع، امضای پیش/پس و وضعیت کامیت در `GITHUB_STEP_SUMMARY`
  درج می‌شود و در شکست، ۴۰ خط آخر لاگ هم بدون نیاز به بارگیری artifact دیده می‌شود.

### `.github/workflows/deploy-pages.yml`

پس از هر push روی `main`، بسته انتشار را می‌سازد (فقط `index.html`، `assets/` و
`data/`) و روی GitHub Pages منتشر می‌کند.

**زنجیره انتشار پس از به‌روزرسانی ربات**: pushهای `github-actions[bot]` رویداد
«push» برای سایر workflowها راه نمی‌اندازند (سد بازگشتی GITHUB_TOKEN). برای همین
`refresh-data.yml` و `weekly-sync.yml` پس از ثبت داده تازه، این جریان را با
`gh workflow run` (یعنی `workflow_dispatch`، که از این سد مستثناست) فرامی‌خوانند.
بدون این حلقه، به‌روزرسانی روزانه روی مخزن می‌نشیند اما سایت منتشرشده تا push بعدی
یک انسان کهنه می‌ماند.

برای فعال‌سازی: در تنظیمات مخزن، **Settings → Pages → Source** را روی **GitHub Actions** بگذارید.

سپس سه اصلاح واقع‌گرایانه اعمال می‌شود:

**۱. نرخ حقیقی.** برای محصولات منابعی، فاصله نرخ اسمی از تورم به‌صورت جریمه وارد می‌شود

**۲. هزینه فرصت.** تسهیلات سپرده‌محور ۵ نمره جریمه می‌گیرند: پولی که برای امتیازسازی خواب
می‌ماند، از بازده بازار محروم می‌شود و تورم آن را می‌فرساید.

**۳. اعتبار منبع.** رکوردهای خودکار، کم‌اطمینان یا نیازمند بازبینی حداکثر ۸ درصد امتیاز
کمتری می‌گیرند.

پروفایل‌های آماده: متعادل، کم‌هزینه‌ترین، دیجیتال‌محور، سریع‌ترین، بدون وثیقه.

### محاسبات مالی

برای سود سالانه، فرمول اقساط مساوی و روش قدیمی سود مازاد موجود است. برای
وام‌های کارمزدمحور، مدل پیش‌فرض **صرفاً برآورد** است: کارمزد سالانه بر مانده
در آغاز هر سال پرداخت و اصل در سایر ماه‌ها تقسیم می‌شود. برای سال ناقص، کارمزد
متناسب با ماه‌های باقی‌مانده است؛ قرارداد بانک ملاک نهایی است. مدل نامعلوم
اعتبار خرید یا اقساط نامنظم برآورد نمی‌شود. `feeModel: one-time` فقط در صورت
وجود شاهد صریح برای کارمزد یک‌باره به کار می‌رود.

نرخ مؤثر از IRR جریان اقساط واقعی مدل و تبدیل مرکب ماهانه به سالانه محاسبه
می‌شود. هیچ هزینه‌ای به‌طور خودکار از اصل کسر نمی‌شود؛ کاربر می‌تواند هزینه
کسر اولیه را صریحاً وارد کند. بازده یا هزینه حقیقی از رابطه دقیق فیشر
`(1 + i) / (1 + π) − 1` محاسبه می‌شود.

مثال تخمینی ۳۰۰ میلیون تومان، ۴٪ کارمزد سالانه و ۱۲۰ ماه:

| مورد | نتیجه تخمینی |
| --- | --- |
| قسط معمول اصل (۱۱۰ قسط) | ۲٬۷۲۷٬۲۷۳ تومان |
| کارمزد سال اول (قسط نخست) | ۱۲٬۰۰۰٬۰۰۰ تومان |
| مجموع کارمزد ده‌ساله | ۶۶٬۰۰۰٬۰۰۰ تومان |
| نرخ مؤثر سالانه مرکب، بدون کسر اولیه | ۴٫۴۸٪ |
| هزینه حقیقی با تورم مفروض ۷۶٫۸٪ | ۴۰٫۹٪− |

کارمزد سال‌های بعد بر مانده نزولی است، نه ۴٪ یک‌باره روی اصل. برای نمونه
[روش توضیح‌داده‌شده رده](https://www.rade.ir/loan-marriage-loan/) و
قرارداد مشخص بانک را بررسی کنید.

### یادداشت صحت‌سنجی

برای وام ۱۰۰ میلیون تومانی با نرخ ۱۸٪ و ۴۸ قسط، قسط دقیق روش جدید **۲٬۹۳۷٬۵۰۰** تومان است
(با شبیه‌سازی جدول استهلاک تأیید شده: مانده در پایان دوره صفر می‌شود). برخی گزارش‌های
رسانه‌ای عدد ۲٬۹۳۸٬۸۶۳ را ذکر می‌کنند که با محاسبه دقیق هم‌خوان نیست؛ مرجع این پروژه
محاسبه ریاضی است و آزمون‌ها آن را قفل کرده‌اند.

نرخ مؤثر تخمینی هزینه‌هایی مانند بیمه، ضامن و فرصت سپرده را در بر نمی‌گیرد؛
اگر هزینه کسر اولیه معلوم باشد باید کاربر آن را وارد کند. این برآورد تضمین نرخ قرارداد نیست.

### سقف مشروط

سقف برخی محصولات یک حق قطعی نیست و به سپرده، امتیاز یا مصوبه اعتباری وابسته است (مثلاً
«چند برابر میانگین حساب»). این رکوردها با نشان `ceilingContingent` علامت می‌خورند و در
جدول مقایسه با نماد «≈» نمایش داده می‌شوند و **در انتخاب مقدار برتر هر ردیف شرکت نمی‌کنند**؛
در غیر این صورت محصولی با سقف چند میلیاردیِ فرضی، برنده «کم‌ترین قسط» می‌شد و مقایسه
بی‌معنا می‌گشت.

### زنجیرهٔ جایگزین منابع

هر منبع در `tools/lib/resilience.mjs` با زنجیرهٔ چهارمرحله‌ای خوانده می‌شود:

```
نشانی اصلی → آینه‌های همان نهاد → آرشیو اینترنت (با تاریخ snapshot) → پروکسی متن
```

قاعده‌ها: دادهٔ آرشیوی هرگز «تازه» جا زده نمی‌شود (سن snapshot در گزارش می‌آید و
snapshot کهنه‌تر از ۹۰ روز «شاهد امروز» شمرده نمی‌شود)؛ صفحهٔ «Page Not Found» با
کد ۲۰۰ دیگر «منبع سالم» ثبت نمی‌شود؛ و منبع جایگزین دادهٔ اصلی را بازنویسی نمی‌کند.
گزارش کامل ممیزی و نقشهٔ بک‌آپ: [`docs/FRESHNESS_AUDIT_2026_11_03.md`](docs/FRESHNESS_AUDIT_2026_11_03.md).

```bash
npm run health      # سلامت منابع و تازگی داده → data/source-health.json
npm run crosscheck  # تطبیق مستقل نرخ‌ها با منابع جایگزین (نیازمند شبکه)
```

نرخ‌ها تابع مصوبات شورای پول و اعتبار و بخشنامه‌های بانک مرکزی است و بانک‌ها می‌توانند
شرایط را تغییر دهند. **پیش از هر اقدام مالی، شرایط را از منبع رسمی بانک تأیید کنید.**

### نکته امنیتی
